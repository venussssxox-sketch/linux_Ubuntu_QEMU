# 前置项目执行计划：Linux 混合 I/O 延迟测量与诊断工具

## 0. 项目定位

这个前置项目用于建立 EdgeIO-Tail 所需的基础能力，同时为两个目标岗位准备可写进简历的成果：

1. **智能硬件嵌入式软件岗位**：RTOS / Linux / BLE / 传感器方向。
2. **工业嵌入式 Linux 底层驱动岗位**：ARM、Linux、通信协议、外设访问和问题定位方向。

项目不直接实现自适应控制器，也不声称已经掌握 RTOS、BLE 或 Linux 内核驱动。它首先证明以下能力：

- 能用 C 在 Linux 下编写可靠的并发程序。
- 能设计并复现实验，而不是只运行现成命令。
- 能记录请求级延迟并计算 P50/P95/P99。
- 能使用 fio、io_uring 和基础 tracing 工具。
- 能从现象、指标和系统证据中定位问题。
- 能整理 README、脚本、原始数据和技术报告。

## 2. 每天的固定工作节奏

每天投入 6 小时：

- **第 1 小时：**阅读当天主题的官方文档或 man page，写 5～10 条笔记。
- **第 2～5 小时：**编码、配置、运行实验或排查问题。
- **第 6 小时：**保存原始结果、写实验记录、提交 Git commit。

每天结束时必须回答：

1. 今天具体完成了什么？
2. 产生了哪些文件或数据？
3. 遇到了什么问题？
4. 明天开始前还缺什么？
5. 这项工作对应哪个岗位要求？

周日休息，不安排新功能；如果前一天出现环境问题，可以用周日补记录和整理，但不要把休息日变成持续加班。

# 第一周：Linux 用户态、C 文件 I/O 和可复现实验

## 第 1 天：建立仓库和实验规则

### 要做什么

- 创建项目目录和 Git 仓库。
- 建立 README、实验记录模板和目录结构。
- 检查 gcc、make、git、python3、fio、iostat、strace、perf 是否可用。
- 记录主机系统、内核版本、磁盘挂载点和可用空间。
- 选择一个安全临时目录，例如项目目录下的 `data/workspace`。

### 怎么完成

- 所有测试只在临时目录中创建普通文件。
- 不直接对 `/dev/nvme*`、`/dev/sd*` 等原始设备写入。
- 在 README 记录每个工具的版本。
- 编写 `scripts/clean.sh`，只能删除项目自己的临时文件。

### 验收

- 空目录可以通过 README 完成初始化。
- `git status` 干净，第一笔 commit 已完成。
- 清理脚本不会触碰项目目录之外的文件。

### 岗位契合

- 对两个岗位都体现工程规范、环境记录和可复现意识。
- 对工业 Linux 岗位尤其重要，因为底层问题必须能复现。

## 第 2 天：C 文件描述符和顺序读取

### 要做什么

- 学习 `open`、`read`、`close`、`errno`。
- 编写单线程程序，按固定块大小读取一个大文件。
- 记录每次读取前后的单调时钟时间。
- 输出 CSV：请求编号、偏移、大小、开始时间、结束时间、耗时、错误码。

### 怎么完成

- 使用 `clock_gettime(CLOCK_MONOTONIC_RAW)` 或同等单调时钟。
- 处理短读、EOF 和系统调用失败。
- 不要只记录总耗时，要保存每次请求的结果。

### 验收

- 能读取至少 256 MiB 的测试文件。
- CSV 行数与成功请求数一致。
- 能解释为什么测量延迟不能使用墙上时间。

### 岗位契合

- 对工业 Linux 岗位：对应 C、Linux 系统调用和问题分析。
- 对智能硬件岗位：对应设备数据链路中的采集和时间戳记录思维。

## 第 3 天：周期日志写入和持久化语义

### 要做什么

- 增加日志写入线程或代码路径。
- 每隔固定时间追加小块日志。
- 比较普通 `write`、`fsync` 和 `fdatasync` 的延迟。
- 记录日志写入是否成功、写入字节数和耗时。

### 怎么完成

- 日志内容包含递增序号和校验信息。
- 设置小日志块，例如 256 B、1 KiB、4 KiB。
- 让模型读取和日志写入使用不同文件，避免把文件偏移混在一起。

### 验收

- 程序退出后日志可以校验序号连续。
- 能说明“写入成功”和“数据已经持久化”不是同一概念。
- 至少得到一张不同同步方式的延迟对比表。

### 岗位契合

- 对工业 Linux 岗位：对应文件系统、可靠性和故障定位。
- 对智能硬件岗位：对应设备日志、状态记录和异常追溯。

## 第 4 天：并发、互斥和错误处理

### 要做什么

- 使用 pthread 创建模型读取线程和日志写入线程。
- 处理共享统计数据的互斥访问。
- 为线程增加退出标志、超时和错误传播。
- 让程序接收命令行参数：文件大小、块大小、运行时间、日志周期。

### 怎么完成

- 使用 `pthread_mutex` 或原子变量保护共享状态。
- 主线程负责等待和汇总，不让工作线程直接决定程序退出。
- 所有错误输出包括操作名、参数和 `strerror(errno)`。

### 验收

- 程序可以正常启动、运行、停止。
- 发送中断信号后能关闭文件并输出汇总。
- 连续运行 5 分钟没有数据竞争或崩溃。

### 岗位契合

- 对两个岗位都体现并发、稳定性和故障处理能力。
- 这比只写一个单线程 demo 更接近真实嵌入式软件工作。

## 第 5 天：统计脚本和延迟分位数

### 要做什么

- 编写 Python 或其他脚本读取 CSV。
- 计算平均值、最小值、最大值、P50、P95、P99。
- 分别统计模型读取和日志写入。
- 绘制延迟分布图和时间序列图。

### 怎么完成

- 明确分位数计算方法，并在报告中写出。
- 保留原始 CSV，不覆盖原始数据。
- 图表标题必须包含测试参数。

### 验收

- 给定同一份 CSV，脚本能重复生成同一结果。
- 图表能看出平均值和 P99 的差异。
- 完成 `reports/baseline.md` 初稿。

### 岗位契合

- 对工业 Linux 岗位：体现性能分析和数据驱动定位。
- 对智能硬件岗位：体现系统集成测试和可靠性验证能力。

## 第 6 天：第一周小结和 ARM64 功能验证

### 要做什么

- 在本机完成同步版本的基本实验。
- 尝试使用已有 Buildroot/QEMU ARM64 环境进行交叉编译或功能运行。
- 记录 x86_64 和 ARM64 之间的差异。
- 整理第一周报告。

### 怎么完成

- ARM64 只做编译、启动、参数解析、日志输出和小文件功能验证。
- 不把 QEMU 的性能结果当作真实硬件性能。
- 保存 QEMU 启动命令和终端日志。

### 验收

- 同步版本在本机运行成功。
- 至少完成一次 ARM64 功能冒烟。
- 第一周报告能回答：程序做什么、如何测量、目前有什么限制。

### 岗位契合

- 对工业 Linux 岗位：直接对应 ARM/Linux 环境适配。
- 对智能硬件岗位：体现跨平台集成和软硬件边界意识。

# 3. 与两个目标岗位的对应关系

## 目标岗位一：RTOS / Linux / BLE / 传感器智能硬件

这个前置项目能证明：

- C 语言和并发编程。
- Linux 应用环境。
- 数据采集、时间戳和日志完整性。
- 自动化测试。
- 性能指标和问题定位。
- 系统集成与边界意识。

它不能证明：

- FreeRTOS 或 RT-Thread 任务调度。
- UART、I2C、SPI、CAN。
- BLE 协议栈。
- 传感器驱动。
- 原理图阅读和硬件联调。

因此投这个岗位时，建议在前置项目之后补一个小模块：使用 STM32 或模拟设备完成 UART/I2C/SPI 数据采集，哪怕规模只有 1～2 周，也比在简历中虚写 BLE 更可靠。

## 目标岗位二：工业嵌入式 Linux 底层驱动

这个前置项目能证明：

- C 和 Linux 系统调用。
- 文件 I/O 和并发。
- io_uring、fio 和性能测试。
- strace、perf、iostat、ftrace 等定位工具。
- ARM64/QEMU 功能移植。
- 可复现构建、测试和技术文档。

它仍然缺少：

- 内核模块和设备树。
- UART、I2C、SPI、DMA 驱动。
- TCP/IP 实际编程。
- RTC、PHY、eMMC、NAND、SD 等外设。
- 真实 ARM 开发板上的联调。

因此投这个岗位时，前置项目可以作为主要项目之一，但最好再加入一个小型 Linux 内核模块或设备树实验，证明你不是只会用户态工具。

# 5. 是否进入 EdgeIO-Tail 的判断

达到以下条件才进入主项目：

1. 能解释一次 read/write/fsync 的基本路径。
2. 能独立设计 fio 参数并说明理由。
3. 能计算并解释 P99。
4. 能写出最小 io_uring 程序。
5. 能用至少一种 tracing 工具定位异常。
6. 能从 README 复现自己的实验。
7. 面试时能不看资料解释项目每个模块。

如果第 1～6 项完成，但第 7 项不稳定，先继续巩固前置项目；如果全部满足，再开始 EdgeIO-Tail 的混合负载和自适应控制部分。
