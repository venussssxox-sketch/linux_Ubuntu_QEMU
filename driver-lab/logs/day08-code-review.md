# Day 8 源码复查：锁、等待与通知

## 复查范围

驱动 read/write/poll/ioctl、FIFO 条件助手、模块与打开文件的生命周期，以及统一回归入口。接口依据本项目使用的 Linux 6.12.27 源码。

## 锁状态检查

| 路径 | 检查结论 |
| --- | --- |
| 零长度读写 | 加锁前返回 0，不访问 FIFO |
| mutex_lock_interruptible 失败 | 未取得锁，直接返回，无需解锁 |
| FIFO 满足条件 | 持锁跳出循环，执行复制后解锁 |
| 非阻塞且条件不满足 | 解锁后返回 EAGAIN |
| 阻塞且条件不满足 | 解锁后 wait_event_interruptible；条件助手自己取得锁 |
| 等待被信号打断 | 不持有 FIFO 锁，直接返回等待错误 |
| 正常唤醒 | 回到循环重新加锁、检查条件，不能假设数据或空间已预留 |
| poll | 先登记两条等待队列，再持锁读取状态，解锁后返回掩码 |
| ioctl | 持锁取得三个字段的一致快照；解锁后 copy_to_user |

当前路径中未发现遗漏解锁或持有 FIFO mutex 进入等待队列的问题。互斥锁允许睡眠，不能简单替换为自旋锁；用户内存拷贝可能触发缺页并睡眠。

## 等待与唤醒

- 成功读出字节后，FIFO 获得空间，通知写等待队列。
- 成功写入字节后，FIFO 获得数据，通知读等待队列与 SIGIO 订阅者。
- wait_event_interruptible 的等待条件会被重新检查，正常返回后驱动仍再次加锁检查，以应对竞争者先消费数据或空间。
- poll_wait 登记队列本身不是在该回调中睡眠；poll 通用框架负责等待。
- 就绪状态和 ioctl 状态都不预留数据、空间或消息边界。

## 实际发现并修复：部分用户拷贝错误

Linux 6.12.27 的 lib/kfifo.c 中，__kfifo_from_user 与 __kfifo_to_user 在部分拷贝故障时返回 -EFAULT，但仍按成功复制量推进 in/out。

旧驱动在 ret != 0 时直接返回，导致实际已传输字节却向用户报告完整失败，并跳过状态变化通知。新增测试用两页匿名映射，将后一页设为 PROT_NONE；先将 FIFO 读写位置移动到环形尾部，再从第一页最后一个字节发起两字节读写，使第二段复制失败。

旧版实际输出：partial fault write: returned=-1 used=1 expected=1/1；该轮原有 10 项通过、新增项失败。

修复：仅在 ret != 0 且 copied == 0 时直接返回错误；部分成功继续通知等待者并返回 copied。读取与写入采用同样规则。新增用例检查部分写入、部分读取的返回值、FIFO 剩余量和剩余字节内容。

## 生命周期与验证边界

- 静态 FIFO、mutex 和等待队列无需 kfree；misc_register/misc_deregister 配对。
- owner 模块引用保护正在使用的模块；release 撤销该打开文件的 fasync 订阅。
- 已有测试验证正常阻塞读写唤醒、poll、SIGIO，以及设备打开期间拒绝卸载。
- 新增部分故障用例直接验证传输返回值和 FIFO 数据，没有单独构造“等待者在部分故障发生时被唤醒”的并发用例；此分支通知逻辑通过源码检查，不能夸大为已直接测试所有时序。
- 重复回归包含单生产者顺序和双生产者总量验证，不等同于所有多读者竞争场景覆盖。
- 尚未进行 KCSAN/lockdep 专项验证、初始化失败注入、8 小时稳定性测试或干净环境完整构建。
